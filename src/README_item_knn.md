# Item-based kNN Recommender System

This document describes the implementation, testing, hyperparameter tuning, and evaluation of the Item-based k-Nearest Neighbors (ItemKNN) recommender system developed for Part 1 of the Recommender Systems project.

The model uses the MovieLens 1M dataset and supports two item-item similarity measures: cosine similarity and Pearson correlation.

## 1. Implementation

**File:** `src/item_knn.py`

The `ItemKNN` class implements an item-based collaborative filtering recommender system.

### Main functionality

- Builds a sparse user-item rating matrix from the training data.
- Computes item-item similarities using cosine similarity or Pearson correlation.
- Selects up to `k` positively similar items previously rated by the user as neighbors for each candidate item.
- Predicts item scores using a similarity-weighted average of the user's ratings.
- Generates Top-N recommendations ranked by predicted score.
- Excludes items already rated by the user.
- Uses deterministic ordering to resolve ties between items with equal scores.

### Main methods

| Method | Description |
|---|---|
| `__init__(k=20, similarity="cosine")` | Initializes the model and its hyperparameters. |
| `fit(train)` | Builds the user-item matrix and computes item-item similarities. |
| `score_items(user_id)` | Calculates prediction scores for candidate items. |
| `recommend(user_id, top_n=10)` | Returns the highest-ranked recommended MovieIDs. |

The model supports two hyperparameters:

- **`k`**: Maximum number of neighbors used to predict each candidate item's score.
- **`similarity`**: Item-item similarity measure (`"cosine"` or `"pearson"`).

The neighborhood size `k` is different from the evaluation cutoff. In this project, recommendations are evaluated at Top-10, regardless of the neighborhood size used by ItemKNN.

## 2. Similarity Measures

### Cosine Similarity

Cosine similarity is computed between item rating vectors using `sklearn.metrics.pairwise.cosine_similarity()`.

The implementation uses the sparse user-item matrix to calculate item-item similarities efficiently. Missing ratings are represented by zeros in the matrix.

### Pearson Correlation

Pearson correlation is computed using ratings from users who have rated both items.

The implementation:

1. Converts the sparse rating matrix to a dense matrix.
2. Represents missing ratings as `NaN`.
3. Computes pairwise Pearson correlations using `pandas.DataFrame.corr(method="pearson", min_periods=2)`.
4. Replaces undefined correlations with zero.

The original loop-based Pearson implementation is preserved as commented code in `item_knn.py` for comparison.

Self-similarities are set to zero for both similarity measures.

### Scoring and recommendation generation

For each candidate item, the model identifies up to `k` positively similar items that the target user has already rated.

The predicted score is calculated as a similarity-weighted average of those ratings:

**Predicted score = sum(similarity × rating) / sum(similarity)**

Only neighbors with positive similarity contribute to the prediction.

Candidate items without valid positive-similarity neighbors receive a score of negative infinity and are excluded from the final recommendations.

Previously rated items are also excluded.

The model ranks the remaining candidate items by predicted score and returns up to `top_n` recommendations.

## 4. Hyperparameter Tuning

**File:** `src/tune_item_knn.py`

Hyperparameter tuning was performed using the temporal training and validation splits.

The objective was to compare different neighborhood sizes and similarity measures before evaluating the selected configuration on the test set.

### Configurations

| Similarity | Neighborhood sizes |
|---|---|
| Cosine | 10, 20, 50 |
| Pearson | 10, 20, 50 |

Six configurations were evaluated.

The tuning script:

1. Loads the temporal training and validation splits.
2. Prepares the validation users and training catalogue using the shared evaluation protocol.
3. Fits ItemKNN using the training data only.
4. Evaluates neighborhood sizes `k=10`, `k=20`, and `k=50` for each similarity measure.
5. Calculates Precision@10, Recall@10, NDCG@10, and Catalogue Coverage.
6. Saves the results to `item_knn_validation_results.csv`.

The similarity matrix is reused across neighborhood sizes to avoid unnecessary recalculation.

### Validation results

| Similarity | Neighbors | Precision@10 | Recall@10 | NDCG@10 | Catalogue Coverage |
|---|---:|---:|---:|---:|---:|
| Cosine | 10 | 0.029065 | 0.013734 | **0.029182** | 0.417531 |
| Cosine | 20 | 0.026016 | **0.014834** | 0.025728 | 0.325778 |
| Cosine | 50 | 0.017276 | 0.008918 | 0.017521 | 0.215729 |
| Pearson | 10 | 0.001829 | 0.000314 | 0.001392 | 0.176679 |
| Pearson | 20 | 0.000813 | 0.000085 | 0.000846 | 0.112780 |
| Pearson | 50 | 0.000203 | 0.000011 | 0.000135 | 0.098307 |

### Selected configuration

**Cosine similarity with `k=10`** was selected because it achieved the highest validation NDCG@10 (0.029182) among the six configurations.

It also achieved the highest validation Precision@10 and Catalogue Coverage.

Although cosine with `k=20` obtained a slightly higher Recall@10, cosine with `k=10` was preferred based on NDCG@10, which accounts for the positions of relevant recommendations.

Pearson correlation performed substantially worse than cosine similarity across all tested neighborhood sizes.

One possible explanation is the instability of pairwise Pearson correlations when items have very few common raters. The implementation permits correlations based on as few as two shared ratings. This is a potential limitation rather than a confirmed explanation of the performance gap.

The selected configuration was subsequently evaluated on the test split without further hyperparameter changes.

## 5. Evaluation Protocol

**Files:**

- `src/evaluation.py`
- `src/test_item_knn_final.py`
- `src/compare_models.py`

The evaluation uses the shared protocol implemented in `src/evaluation.py`.

### Data splitting

MovieLens 1M ratings are ordered by timestamp and divided into:

- **Training:** First 80% of ratings.
- **Validation:** Next 10% of ratings.
- **Test:** Final 10% of ratings.

The split is temporal rather than random.

Training data is used to fit the recommender.

Validation data is used for hyperparameter tuning.

Test data is reserved for the final evaluation and model comparison.

### Relevant items

A movie is considered relevant when the user's rating is **4 or 5**.

The same relevance threshold is used for all evaluated models.

### Evaluation users and catalogue

The shared `prepare_evaluation_data()` function selects users who:

- Appear in the training data.
- Have at least one relevant evaluation interaction involving a movie present in the training catalogue.

The evaluation data is restricted to eligible users and movies known from training.

The catalogue consists of the **3,662 movies present in the training split**.

This protocol ensures that the compared recommenders are evaluated using the same eligible users and candidate catalogue.

Users who do not appear in training are not evaluated because the ItemKNN implementation requires an existing user profile.

### Evaluation metrics

Four metrics are calculated:

- **Precision@10:** Proportion of the ten recommended movies that are relevant.
- **Recall@10:** Proportion of the user's relevant evaluation movies appearing in the Top-10 recommendations.
- **NDCG@10:** Ranking quality, giving greater weight to relevant movies appearing near the top.
- **Catalogue Coverage:** Proportion of movies in the training catalogue recommended to at least one evaluation user.

Precision@10, Recall@10, and NDCG@10 are averaged across eligible evaluation users.

Catalogue Coverage is calculated across the combined recommendations generated for those users.

## 7. Comparison with Most Popular

**File:** `src/compare_models.py`

The selected ItemKNN configuration was compared against two Most Popular variants:

1. **Most Popular (all ratings):** Ranks movies by their total number of training ratings.
2. **Most Popular (positive ratings):** Ranks movies by the number of training ratings equal to 4 or 5.

Both Most Popular variants were retained in the comparison because Part 1 requires reporting at least two variants.

All three models were evaluated using the same training data, eligible test users, catalogue, and evaluation metrics.

### Test results

| Model | Precision@10 | Recall@10 | NDCG@10 | Catalogue Coverage |
|---|---:|---:|---:|---:|
| Most Popular (all ratings) | 0.173690 | 0.048533 | 0.186546 | 0.037138 |
| Most Popular (positive ratings) | **0.181855** | **0.053533** | **0.197313** | 0.035227 |
| ItemKNN (cosine, k=10) | 0.044052 | 0.013980 | 0.044228 | **0.545877** |

The comparison is saved to `model_comparison_test.csv`.

### Discussion

Both Most Popular variants outperform ItemKNN on Precision@10, Recall@10, and NDCG@10.

Most Popular based on positive ratings achieves the highest values for all three relevance metrics.

However, ItemKNN achieves substantially higher Catalogue Coverage.

Specifically:

- Most Popular (all ratings) covers approximately **3.71%** of the training catalogue.
- Most Popular (positive ratings) covers approximately **3.52%**.
- ItemKNN covers approximately **54.59%**.

These results show a trade-off between relevance and catalogue coverage.

Most Popular concentrates recommendations on a relatively small number of frequently rated movies. This produces stronger relevance metrics under the current evaluation protocol but limits catalogue coverage.

ItemKNN generates recommendations from item-item similarities and the user's rating history, resulting in a wider range of recommended movies.

Nevertheless, greater catalogue coverage does not necessarily imply better personalization or recommendation quality. ItemKNN's lower relevance metrics indicate that its recommendations were less successful at recovering relevant test items under this protocol.

The results also depend on the temporal split, the relevance threshold, and the exclusion of unknown users and movies.
